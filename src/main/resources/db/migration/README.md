# DB 마이그레이션

배포하면 Flyway가 이 폴더의 SQL을 버전 순서대로 실행한다. 손으로 ALTER를 돌릴 일은 없다.

## 파일 이름

`V{버전}__{설명}.sql` — 밑줄 두 개다. 예: `V3__add_notice_pinned.sql`
버전은 이어서 올린다. 운영에 이미 적용된 파일은 **절대 고치지 않는다.**
내용이 바뀌면 체크섬이 달라져 다음 배포가 통째로 멈춘다. 고칠 일이 있으면 새 버전을 만든다.

## 언제 쓰나

`ddl-auto=update`는 **없는 것을 추가**할 뿐, 이미 있는 것을 **바꾸지 않는다.**

| 작업 | 담당 |
|---|---|
| 새 테이블, 새 컬럼 | ddl-auto (자동) |
| 컬럼 타입·제약 변경, 컬럼·테이블 삭제, 인덱스 정리, 데이터 보정 | **Flyway** |

행이 이미 있는 테이블에 `not null` 컬럼을 기본값 없이 추가하는 것도 ddl-auto가 실패하는 경우다.
Hibernate는 이때 경고만 남기고 앱을 정상 기동시키므로, 배포는 성공한 것처럼 보이고 해당 API만 죽는다.
`@Column(columnDefinition = "... default ...")`로 기본값을 주거나 여기에 마이그레이션을 쓴다.

## 주의

- SQL은 **MySQL 문법**으로 쓴다. 로컬·테스트는 H2라서 Flyway를 꺼뒀다(`spring.flyway.enabled: false`).
  스키마는 ddl-auto가 만든다.
- Flyway는 Hibernate보다 **먼저** 돈다. 새 환경에는 테이블이 아직 없으므로,
  기존 테이블을 건드리는 마이그레이션은 대상이 있을 때만 실행되도록 감싸는 편이 안전하다
  (`V2__widen_enum_columns_to_varchar.sql` 참고).
- 운영 DB에는 이미 테이블이 있어 `baseline-on-migrate: true`로 현재 스키마를 버전 1로 인정한다.
  그래서 첫 마이그레이션이 V2부터 시작한다.
